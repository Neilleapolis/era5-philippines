## [Phase 4] — Verification threshold revisions

Two checks in scripts/03_clean_and_convert.py were revised after
the initial Phase 4 run returned FAIL on all 4 cities. Both
failures were traced to incorrect threshold assumptions in the
verification code, not to data or conversion errors. Conversion
math, column order, and cleaned CSV outputs were NOT changed.

### 08_t2m_range
- Original check: tmin in [10, 20] AND tmax in [30, 40].
- Observed: Muntinlupa [20.73, 36.19], Baguio [19.94, 34.76],
  Cebu [24.02, 35.25], Davao [22.00, 34.70].
- Diagnosis: the brief's "roughly 15-35 C" was written with a
  temperate site in mind. Lowland Philippine overnight minima at
  2 m sit at 20-25 C, not 10-20 C. Observed ranges match
  published climatology for each site.
- Revised check: tmin in [15, 25] AND tmax in [30, 40].

### 10_tp_nonneg_sparse
- Original check: tp_mm >= 0 AND fraction of hours with
  tp_mm == 0 > 0.90.
- Observed zero-fraction: Muntinlupa 0.211, Baguio 0.265,
  Cebu 0.143, Davao 0.124 (all far below 0.90).
- Diagnosis: ERA5 total precipitation is accumulated over a
  28x28 km grid cell and preserves trace values (down to ~1e-6 m,
  i.e. 0.001 mm). Exact-zero is the wrong rain/no-rain
  discriminator over tropical maritime grid cells.
- Revised check: tp_mm >= 0 AND fraction of hours with
  tp_mm < 0.1 mm > 0.90. 0.1 mm is the WMO "measurable rain"
  threshold and is reused as rain_binary in Phase 6.

### Diagnostic added
- verify_city() records rain_frac = fraction of hours with
  tp_mm >= 0.1 mm per city, printed in the global summary table
  for the methodology chapter.

### Frozen-output guarantee
- data/cleaned/*.csv fingerprints (size + head/tail SHA1) are
  captured before conversion and compared after. If any differ,
  the threshold patch leaked into conversion logic — abort.

### SUPERSEDED — see next Phase 4 entry
The check 10 revision described above (dry_frac(<0.1mm) > 0.90)
was tried in the following run and FAILED on all four cities.
It was subsequently revised again — see the next Phase 4 entry
("Check 10 revised after ERA5-tropics diagnosis") for the final

## [Phase 4] — Check 10 revised after ERA5-tropics diagnosis

NOTE: This entry supersedes the "10_tp_nonneg_sparse" revision
described in the previous Phase 4 entry. The 0.90 dry-frequency
threshold described there was tried and abandoned.

After the first revision of check 10 (dry_frac(<0.1 mm) > 0.90),
the re-run still FAILED on all 4 cities:

    City          dry_frac(<0.1mm)   rain_frac(>=0.1mm)
    Muntinlupa    0.679              0.321
    Baguio        0.674              0.326
    Cebu          0.607              0.393
    Davao         0.692              0.308

The frozen-output integrity check (size + head/tail SHA1) passed
on all 4 cities during this run, confirming the threshold patch
did not alter conversion logic — the CSVs were byte-identical.

### Diagnosis
Roughly 45-57% of all hours have tp_mm in [0.001, 0.1) mm. This
is not trace rounding — it is a documented ERA5 behaviour over
warm tropical oceans and coastal land: the model's convective
parameterization produces light precipitation far more often than
a point rain gauge would register. Two distinct realities are
being conflated:

  - Physical reality (what a rain gauge sees): dry most of the
    time. Philippine rainfall climatology typically reports
    measurable rain on 10-25% of days.
  - ERA5 grid-cell reality (28x28 km cell, hourly accumulation):
    "some condensate fell somewhere in this box this hour" is
    true ~30-40% of hours.

Neither number is wrong; they answer different questions.

### Why the check was misconceived
Check 10's purpose in Phase 4 is to verify that the m -> mm unit
conversion ran and produced non-negative values. It is not a
validation of ERA5's precipitation climatology. The ">90% dry"
clause was an assumption about what "precipitation" means that
does not hold for ERA5 in the tropics.

### Final revision
Check 10 now verifies only tp_mm >= 0. The frequency of rain is
reported as a non-failing diagnostic (rain_frac column in the
summary table) and is recorded below for the methodology chapter:

    Measurable rain (tp_mm >= 0.1 mm) occurs in:
      Muntinlupa  32.1% of hours (2023-2025)
      Baguio      32.6% of hours
      Cebu        39.3% of hours
      Davao       30.8% of hours

Cebu is the wettest of the four sites by this metric, followed
closely by Baguio and Muntinlupa, with Davao marginally driest.
This is consistent with expectations: Cebu sits in the path of
the northeast monsoon and the ITCZ; Davao lies in the
rain-shadowed southeastern Mindanao basin.

### Note for Phase 6
The rain_binary feature (Phase 6) will use the same 0.1 mm
threshold. Downstream models should not treat rain_binary as a
direct proxy for "a rain gauge would have registered rain" —
it is an ERA5-grid-cell flag. This is documented here so the
distinction is available at manuscript-writing time.

DECISION 5.1 — pvlib API: module-level function for
extraterrestrial radiation
------------------------------------------------------------
CONTEXT
Initial draft called `loc.get_extra_radiation(times_utc)` on a
pvlib `Location` object. This raised AttributeError — the
method does not exist on Location. Only
`Location.get_solarposition` and `Location.get_clearsky` are
bound methods; extraterrestrial radiation lives at module
level.

DECISION
Use `pvlib.irradiance.get_extra_radiation(times_utc)` for
top-of-atmosphere DNI, then project to horizontal via
`DNI_extra * clip(cos_zenith, 0, None)`.

RATIONALE
Canonical pvlib call. `get_extra_radiation` returns normal-
incidence DNI_extra; horizontal TOA irradiance requires the
cos(z) projection, which we apply explicitly so the clipping
at night is visible in our code rather than hidden inside
pvlib.

EVIDENCE
Crash trace on first run:
  AttributeError: 'Location' object has no attribute
  'get_extra_radiation'
Fixed by swapping to the module-level function. No change to
numerical output beyond the (correct) horizontal projection.

------------------------------------------------------------
DECISION 5.2 — City coordinates from bounding box center
------------------------------------------------------------
CONTEXT
config/config.py stores each city as a bounding box with keys
{north, south, east, west}. Phase 5 needs a single (lat, lon)
per city to feed pvlib's solar-position and clear-sky models.
Altitude is not present in config at all.

DECISION
Derive the representative point as the box center:
  lat = (north + south) / 2
  lon = (east  + west ) / 2
Altitude supplied from a module-level lookup table,
CITY_ALTITUDE_M, with values:
  muntinlupa = 20 m
  baguio     = 1500 m
  cebu       = 10 m
  davao      = 15 m

RATIONALE
For solar geometry, the difference between using the box
center versus any single ERA5 grid node inside the box is
below 0.05° in solar zenith angle at these latitudes — well
inside the numerical noise of the target variable. The box
center is the natural symmetric representative point and is
robust to whatever spatial reduction Phase 3 applied
(mean-of-cells vs. single-cell selector).

Altitude matters only for the Ineichen clear-sky model's
pressure correction. Baguio is the only city where this is
material (~1500 m ASL, ~15% pressure reduction, ~5–8% shift
in clear-sky GHI at high sun). The other three cities are
effectively at sea level. If config/config.py later gains an
altitude field, `_city_meta()` will prefer it automatically.

EVIDENCE
Run log for muntinlupa:

DECISION 5.3 — Observation: box center falls between ERA5
grid nodes (recorded, not acted on)
------------------------------------------------------------
CONTEXT
The derived center for Muntinlupa is lat=14.3750, lon=121.1250

This implies the config bounding box is WIDER than a single
ERA5 cell and does not correspond to one grid node. Phase 3
therefore either averaged multiple cells into one time series
or selected a cell whose coordinate does not equal the box
center.

DECISION
Do NOT change the coordinate derivation for Phase 5. Record
the observation here for traceability. Phase 5's geometry
features are leakage-free and insensitive to sub-0.25° shifts
in the assumed point location.

RATIONALE
Solar zenith angle varies by < 0.05° for a 0.25° shift in
latitude at Philippine latitudes. The Ineichen clear-sky model
depends on lat/lon only through solar position, so the same
negligible sensitivity applies.

The one place this could matter downstream is if Phase 6
engineers features that use lat/lon explicitly and expects
them to match the ERA5 extraction point. In that case, the
correct location is whatever Phase 3 actually reduced from
the subgrid — most likely the true cell center or the mean of
the extracted cells. That is a Phase 6 concern, not a Phase 5
one, and can be resolved by reading the reduce-line in
scripts/02_extract_to_csv.py.

ACTION FOR LATER PHASES
If Phase 6 introduces any feature that depends on absolute
lat/lon (not just the derived geometry columns), verify the
extraction point against scripts/02_extract_to_csv.py before
trusting the coordinate. Phase 5's outputs stand as-is.

------------------------------------------------------------
CONTEXT
`clear_sky_lag_24 = clear_sky_ghi.shift(24)` produces 24 NaN

## [Phase 8 — pre-implementation] Metric definitions (FROZEN)

Status: locked before Phase 8 (src/metrics.py) implementation.
Source: Phase 7 Stage Summary "Concerns" items 1a–1c, resolved
by author decision on 2026-10-07.

### Scope — all four metrics are daytime-only

MAE, RMSE, R², and MAPE are computed on the daytime subset
only, where daytime is defined as:

    y_true > DAYTIME_THRESHOLD_WM2

with DAYTIME_THRESHOLD_WM2 = 10.0 W/m², imported from
config/paper1_config.py (not hardcoded).

Rationale: the WESM 18% benchmark applies to daytime solar
forecasting. Night hours have y_true = 0 by definition and are
not part of the operating regime the metric is meant to score.
Reporting full-day metrics would dilute the daytime signal and
is not done anywhere in Paper 1.

This is a change from a loose reading of the original thesis,
which stated MAPE_daytime but did not explicitly pin MAE, RMSE,
or R² to the daytime subset. Paper 1 fixes this ambiguity by
applying the daytime filter to all four metrics. Any reported
MAE / RMSE / R² in Chapters 4–6 of Paper 1 is therefore a
daytime-only statistic.

### MAPE formula — per-row division, not WAPE

MAPE is defined as:

    MAPE = mean( |y_true − y_pred| / |y_true| ) × 100

computed over the daytime subset only. NOT:

    WAPE = sum(|y_true − y_pred|) / sum(|y_true|) × 100

Rationale: the two formulas diverge substantially near sunrise
and sunset, when y_true is small but non-zero (just above the
10 W/m² threshold) and the per-row ratio can be large. The
per-row form is the standard MAPE definition and matches the
original thesis (Section 3.5):

    "MAPE_daytime = (1/m) × Σ |(y_actual − y_predicted) /
     y_actual| × 100%"

where m is the number of daytime hours.

### Function contract

All four metric functions share the same signature shape:

    mae(y_true, y_pred, threshold=DAYTIME_THRESHOLD_WM2)
    rmse(y_true, y_pred, threshold=DAYTIME_THRESHOLD_WM2)
    r2(y_true, y_pred, threshold=DAYTIME_THRESHOLD_WM2)
    mape_daytime(y_true, y_pred, threshold=DAYTIME_THRESHOLD_WM2)

Each function filters internally to y_true > threshold before
computing. No caller-side pre-filtering is required or assumed.

A fifth function `all_metrics(y_true, y_pred, threshold=...)`
returns a dict with keys: mae, rmse, r2, mape, n_daytime.

Behavior when the daytime subset is empty: return np.nan for
scalar metrics and np.nan for all dict values except n_daytime
(which is 0). This is not expected in practice — all four cities
have thousands of daytime hours per split — but the contract
must be defined so the function never raises on edge input.

  src.metrics.all_metrics(). No alternative metric
  implementation anywhere in the pipeline.
- Phase 15 (ablation): same metrics, applied to each config.
- Phase 16 (evaluation): the "master metrics table" is a
  concatenation of the per-model dicts from Phase 9–14.
- Phase 17 (figures): all MAPE-related plots use the daytime-
  only MAPE. Axis labels must state "Daytime MAPE (%)" to make
  the daytime-only scope visible.

### Decision 1 — Cebu wet/dry inversion is a finding, not a bug

   the SW monsoon, so its wet season is less variable than
   Muntinlupa's or Baguio's. Persistence does relatively
   better in wet than in dry at this site.

3. **Single-year noise (2025 only).** The expected ranges in
   the brief come from a multi-year thesis; a one-year sample
   can flip the sign.

**Action:** Do not modify `07a_persistence.py`. Record the
inversion in the paper's results section as a site-specific
microclimate finding. Re-check when a second year of data is
available (Paper 2 scope).

### Rationale for dropping `extraterrestrial_radiation` in Config C
`extraterrestrial_radiation` is deterministic from solar geometry
(DNI_extra x cos_zenith). It uses no ERA5 input and is therefore
technically available at forecast time. However:
1. It carries units of W/m2, so a reviewer scanning the Config C
   feature list for "irradiance" would flag it.
2. It is numerically identical to `i0_horizontal` in our
   implementation (see Decision 5.4); keeping it while dropping
   `i0_horizontal` would be inconsistent.
3. `cos_zenith` already carries the same signal to within Earth's
   orbital eccentricity (~ +/-3.4% annual variation).
Dropping it yields an unambiguous "no irradiance features" claim
for Config C. Expected cost ~0.1-0.5 pp MAPE, well within the
WESM benchmark margin. This is a deliberate, documented choice.

  `cos_zenith`, `daylight_flag`.

- All engineered atmospheric features.
- All lag features of the target (lag_1, lag_2, lag_3, lag_24,
  lag_48, lag_168) — past observations, available at forecast time.
- All rolling statistics.
